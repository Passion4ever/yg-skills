# catch-me-up

> 这一类技能的五段骨架、为什么这么定，见 [`../README.md`](../README.md)。约定由 `tests/test_common_ground.py` 强制。

用户跟不上的时候，**停下所有推进工作**，按固定格式重建全景，并交代每一个他没点头就被当成前提的决定。

**成功标准**：用户读完之后，能用自己的话说出「我们在做什么、做到哪了、为什么这么做」。做不到这一点，格式再整齐也是失败。

## 它不做什么

- **不产出任何新工作**——不写代码、不跑分析、不提新方案、不「顺便做一下」
- **不把原话再讲一遍**——原话已经失败过一次了，必须换一套说法
- **不改用户的叫法**——他说「那个筛选」，就叫「那个筛选」，不改口成「预处理流程」
- **不写「详见上文」**——每张表都要有内容，宁可写得笨

## 自动触发

这个技能**没有** `disable-model-invocation`，所以除了敲 `/catch-me-up`，模型读到 description 里的触发词也会自己启动。

这是刻意的：用户说「等一下 / 我没跟上」的时候，正是他没意识到该敲命令的时候。要靠他自己想起来敲，这个技能一半的价值就没了。

代价是可能误触发，所以 description 划了条边界：**对整体方向的困惑**才算，对某个具体技术点的疑问不算——那种直接回答就行。

## 输出格式

五节，标题原样照抄，不增不减不改顺序。某节没内容写「无」，不删标题。

| 节 | 内容 | 硬约束 |
|---|---|---|
| ① 一句话 | 这个项目在做什么 | 30 字以内，不许有专有名词 |
| ② 全景 | 最初目标 / 已完成 / 正在做 / 计划但没做 | 「正在做」只能有一条，跑散了就照实写并注明 |
| ③ 名词表 | 这次对话出现过、用户可能不熟的词 | 解释里不许再出现另一个需要解释的词 |
| ④ 每一步是怎么决定的 | 从**用户最后一次说「可以」**往后，逐条列动作与转向 | 每条标「你定的 / **我定的**」 |
| ⑤ 请你拍板 | 从「我定的」里挑一条真正影响走向的 | **一次只问一个**，然后停下等 |

### ④ 是这个技能的重点

「我定的」包括：选了这个方法而没选另一个、排除了哪些数据或情况、假设了什么条件成立、把哪个问题判定为不重要而跳过了。

**这一列全是「你定的」是可疑信号，不是好消息**——说明没有认真回溯，得回去重找。

## 完成条件

用户明确说继续。在他说之前，不推进任何工作。

如果用户的回应里还带着困惑（「所以呢」「那这个是干嘛的」），**不算完成**——回到 ③ 和 ④，把没说清的那一条重讲。
