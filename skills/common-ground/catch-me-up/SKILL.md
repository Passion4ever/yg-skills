# 停下来对齐

**成功标准**：用户读完之后，能用自己的话说出「我们在做什么、做到哪了、为什么这么做」。做不到这一点，格式再整齐也是失败。

激活期间**不做**：不写代码、不跑分析、不提新方案、不推进下一步、不「顺便做一下」。

## 怎么做

**换一套说法，别把原话再讲一遍**——原话已经失败过一次了。

**用户管它叫什么就叫什么。** 他说「那个筛选」，别改口成「预处理流程」。

**每张表都要有内容。** 宁可写得笨，不要写「详见上文」。

## 输出格式

照抄下面的骨架填。**标题原样照抄，不增不减不改顺序**。某节确实没内容就写「无」，不要删掉标题。

---

### ① 一句话

<当前这个项目在做什么，30 字以内，不许有专有名词>

### ② 全景

- **最初目标**：<用户一开始要的东西，不是中途演化出来的>
- **已完成**：<编号，一条一行，每条 15 字以内>
- **正在做**：<只能有一条。如果实际上在同时推进多条，照实写出来并注明「这里跑散了」>
- **计划做但还没做**：<编号，一条一行>

### ③ 名词表

只列这次对话里出现过、且用户可能不熟的词。解释里不许再出现另一个需要解释的词。

| 名词 | 人话 |
|---|---|

### ④ 每一步是怎么决定的

从**用户最后一次明确说「可以」的地方**往后，按时间顺序列出每一次动作和转向。

| # | 做了什么 | 为什么 | 谁定的 |
|---|---|---|---|
| 1 | | | 你定的 / **我定的** |

「我定的」包括：选了这个方法而没选另一个、排除了哪些数据或情况、假设了什么条件成立、把哪个问题判定为不重要而跳过了。

### ⑤ 请你拍板

从上一节标「我定的」里，挑出**真正影响后续走向**的那一条，问用户一个问题。**一次只问一个，然后停下来等。**

---

骨架之外不要多写。① 和 ③ 各有一种糊弄法——**都是照着规则写、看起来还挺齐整的那种**：

| | ✗ | ✓ |
|---|---|---|
| ① 用专有名词把话说回去 | 用 LightningCLI 重构 config 的继承链 | 把散在各处的训练参数收到一个文件里改 |
| ③ 解释里又出现要解释的词 | 检查点：保存模型权重的 checkpoint | 检查点：训练到一半存下来的存档，能从这儿接着跑 |

**④ 全是「你定的」是可疑信号**，不是好消息——说明没有认真回溯，回去重找。

## 完成条件

用户明确说继续。在他说之前，不推进任何工作。

如果用户的回应里还带着困惑（「所以呢」「那这个是干嘛的」），不算完成——回到 ③ 和 ④，把没说清的那一条重讲。
