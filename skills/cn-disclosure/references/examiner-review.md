# 外部审查员评审

**阶段 4 末尾读本文件做首轮评审**,阶段 7 定稿前再照它做一次收尾复核(范围只限首轮之后改动过的部分)。第一次评审不要放到阶段 7——那时权项和说明书已定稿,改一处要牵动四处。

四个校验器只查形式与溯源,查不了实质。实质问题(权项是否清楚、是否得到支持、公开是否充分、创造性论证是否闭环)要另一个模型以审查员视角读一遍。

用 `mcp__codex__codex` 调 `REVIEWER_MODEL`,推理强度 `high`。喂全文,提示词按下列结构:

```
你是国家知识产权局的发明专利实质审查员。以下是一份技术交底书全文。

请按《专利法》与《专利审查指南》逐条审查，只报告你能指出具体位置和具体理由的问题：

- 第 22 条：新颖性、创造性。独立权利要求相对现有技术的区别技术特征是什么？
  该区别能否解决所声称的技术问题？技术问题—技术手段—技术效果是否闭环？
- 第 25 条：是否落入智力活动的规则和方法。算法类发明是否锚定到具体技术领域的
  数据与技术效果，而非纯粹的数学方法？
- 第 26.3 条：公开充分性。本领域技术人员照此能否实现？哪一步缺少必要的实施细节？
- 第 26.4 条：清楚性与支持。权利要求的每个技术特征是否在说明书中有对应记载？
  有无使用功能性限定、结果性限定、含义不清的术语？
- 第 33 条视角：现在写下的内容，日后不得增加。有哪些应当写而未写、将来无法补入的内容？

每条问题给出：所在位置（权项号或章节）、问题性质（对应法条）、严重程度
（致命 / 需修改 / 建议）、以及一个具体的修改方向。

不要给出笼统的评价。不要重复交底书原文。
```

**把它的每一条都当作待核实的断言,不是结论。** 逐条回到证据台账与源材料核过,再决定采纳、部分采纳还是不采纳,并记录不采纳的理由。

已知的失误模式(据一次实际评审的统计):

- **多数条目有用**,但会有若干条方向相反——把已经正确的地方判成错的。核过再动手,否则会按错误意见把对的改坏。
- **它会漏掉最严重的问题。** 那次它没发现权利要求里有一条技术特征被写成了源码中并不存在的形式;那是全篇最重的错,最后是逐行比对代码才查出来的。
- 因此:**评审是补充,不是替代**。阶段 1 的交叉核实、四个校验器,一样都不能省。

若 `mcp__codex__codex` 不可用,跳过本步,不要因此中断流程——但**跳过要留痕**:把
`evidence.json` 的 `metadata.assurance.external_review` 记成 `{"done": false, "reason": "…"}`。
校验器查这一条(`ASSURANCE_NO_REASON`),出稿时它会印在交底书表头,代理师翻开第一页就看得见。

做了的同样要留痕:`{"done": true, "model": "实际用的型号"}`。型号会过期,记下来才知道
一年后回看这份稿子当时是被谁审的。
